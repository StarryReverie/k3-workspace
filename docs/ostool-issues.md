# ostool 的已知问题与改进建议

适用版本：ostool 0.31.1
使用环境：BananaPi BPI-SM10（SpacemiT K3），Alpine 3.23.4
记录时间：2026-11-09
相关文档：[`ostool-basics.md`](ostool-basics.md)、[`alpine-recovery.md`](alpine-recovery.md)

本文记录实际使用中遇到的问题，并给出改进建议。问题来自 ostool 与平台两侧，文中不再逐条区分。

## 0. 总体判断

问题可以归为三层：

- 接入方式：宿主机只能通过串口接触开发板，串口速率低且没有流控。
- 会话抽象：ostool 把会话当作一次性的底层连接，而不是可以持有的开发环境。会话编号因此出现在上传、下载、执行等每个操作中，用户必须自己维护状态。
- 工程集成与规范：缺少常用的文件传输与自动化命令，配置文件与凭证的位置也不符合现有约定。

第 2 节与第 3 节的问题大多来自同一个设计选择，即会话没有被抽象成可复用的上下文。后文不再重复这一前提。

## 1. 连接与开发板选择

### 1.1 只有串口，链路不稳定

宿主机与开发板之间没有网络路径，只能通过串口转发交互。开发板本身接入了 `192.168.1.0/24` 网段，但宿主机没有通往该网段的路由，因此开发板内运行的 sshd 无法从宿主机连接。

串口速率为 115200，没有硬件流控。输入存在两类问题：BusyBox ash 在显示提示符前发送 `ESC[6n` 查询光标位置，行首会丢失一个字符；一次性粘贴较长内容时，字符以突发方式写入，中间部分被丢弃。

影响：长命令难以输入；无法远程协作；每次操作都需要人工监视串口输出；自动化几乎不可行。

当前可用：用 `scripts/capture-session.sh` 保留会话日志，命令分行输入，出现字符丢失时整行重新输入。

建议：为实验网络提供虚拟专用网络（VPN）入口或跳板机，使宿主机能够访问 `192.168.1.0/24`，从而直接使用开发板内已有的 sshd；串口保留为救援通道。ostool 侧同时处理 1.4 的输入节流问题。

### 1.2 无法指定具体开发板或镜像

`ostool board connect -b BananaPi` 由服务端分配开发板。平台至少有两块 BananaPi，分别运行 Alpine 与 Yocto，行为完全不同。附加 `--board-id` 时，平台可能拒绝请求，也可能仍分配到另一块开发板。

影响：同一套命令在不同会话中表现不同；针对 Alpine 的步骤可能在 Yocto 上失败；无法固定使用某一块开发板。

当前可用：连接后查看 `/etc/os-release` 确认镜像；分配到不符合预期的开发板时重新连接。

建议：`ostool board ls` 输出镜像、序列号或位置等属性；连接时支持按镜像或序列号筛选；返回实际分配到的开发板信息，而不是只返回板型。

### 1.3 交互连接不会自动停在 U-Boot

`ostool board connect` 只转发串口，U-Boot 的自动启动窗口约为 3 秒，必须在窗口内手动按 `Ctrl+C`。`ostool board run` 会在后台周期性发送 `Ctrl+C`，但该行为没有提供给交互连接使用。

影响：进入 U-Boot 依赖按键时机；错过窗口后开发板继续启动系统，只能断开重连。

建议：为 `board connect` 增加 `--stop-at-uboot` 选项，复用 `board run` 已有的中断逻辑；启动窗口的长度可配置；在串口输出中给出明确的提示。

### 1.4 输入不做节流，粘贴时字符丢失

ostool 按终端交付的速度转发输入，没有字符间隔，也没有利用流控。粘贴时，整段内容一次性交给转发层，而转发层到串口的速率只有 115200；缓冲区不足时，中间的字符被丢弃。串口没有硬件流控，丢弃后无法恢复。

影响：粘贴不可用；长地址与长命令必须拆成多段；输入错误只能在整行重来。

建议：按可配置的间隔发送字符，例如每个字符间隔数毫秒；识别粘贴操作并降低发送速率；串口支持时启用硬件流控；在本地维护输入缓冲，发送后校验回显，不一致时重发。

### 1.5 板级初始化依赖不可解释的寄存器操作

初始化网卡需要在 U-Boot 中执行一组命令，其中包含对 `0xd4282bf0` 的读改写，以及对 `0x10001` 的按位或操作。这些地址与数值的含义在可用的配置与文档中没有说明，只能从已验证的配置文件中复制。

影响：板级配置难以维护；更换固件版本时无法判断是否仍然适用；错误地用于其他板型可能产生未知后果。

建议：由 ostool 提供板级配置档案，按板型与固件版本选择；将网卡初始化封装为有名字的动作，例如 `ethernet-init`；至少在配置中注明寄存器的作用与来源。

## 2. 会话模型

### 2.1 所有操作都要手动指定会话编号

ostool 不保存当前会话。上传接口、文件共享地址、后续操作都需要用户自己提供会话编号（`session_id`）。本仓库用 `scripts/session-env.sh` 从日志中提取编号并导出为 `SID`，但这是用户侧的补充实现，不是 ostool 的能力。

影响：每条命令都要先准备会话编号；编号过期后返回 404；脚本依赖日志格式，日志缺失或格式变化时失效。

当前可用：连接时使用 `scripts/capture-session.sh`，操作前执行 `source scripts/session-env.sh`。

建议：增加本地会话上下文，例如 `ostool board use` 将当前会话写入本地文件，后续命令默认使用该会话；同时提供 `OSTOOL_SESSION` 环境变量，便于脚本读取；`ostool board status` 显示当前会话与剩余时间。

### 2.2 下载地址也要求会话编号

开发板内的下载地址格式为：

```text
http://192.168.1.2:2999/share/sessions/<session_id>/boot/<file>
```

同一时刻一块开发板只属于一个会话，从开发板的角度看，会话编号是冗余的。但地址中仍然必须包含它，而且编号有 36 个字符。

影响：在串口输入不稳定的情况下，这个地址几乎无法手工输入；粘贴又会造成字符丢失；编号写错时只得到 404，无法判断是过期还是输错。

建议：由服务端提供按开发板名称解析的稳定地址，例如 `http://<board-name>/share/...`，由服务端映射到当前会话；或在登录时把基地址写入环境变量与 `/etc/motd`；ostool 提供 `board url <path>` 直接输出完整地址。

### 2.3 会话不能分离与重连

关闭客户端即结束会话。连接异常中断后没有 `attach` 之类的恢复方式，只能重新连接并重新上电。终端崩溃或网络抖动都会导致当前进度丢失。

影响：长时间操作无法跨越终端故障；无法在多个终端之间切换；调试过程中断后需要重新开始。

建议：支持分离与重新接入，例如 `--detach` 与 `board attach`；客户端断开后保留一段时间的会话；保留最近的输出缓冲，重新接入时补发。

### 2.4 会话时限不可控

据社区文档，平台会在约 5 分钟后回收会话。客户端会发送保活请求，但用户无法配置时限，也无法延长。`board run` 可能在判活阶段遇到会话被回收，即使串口日志中已经出现成功标记。

影响：编译、传输等长任务容易被中断；自动化流程需要在每一步之后重新建立会话。

建议：提供可配置的空闲时限与保活间隔；回收前给出提示；`board run` 在已经匹配成功标记时，不因会话回收而判定失败；允许在会话即将到期时申请延长。

## 3. 自动化与文件传输

### 3.1 上传等基本操作需要用户自行实现

上传文件需要用户自己发 HTTP 请求，携带访问令牌与文件路径请求头，并从返回的 JSON 中取出地址。当前版本没有提供上传、下载、列出文件或删除文件的命令。

影响：每个使用 ostool 的项目都要重复实现同一套脚本；令牌处理、错误重试、进度显示都要自行编写；不同项目的实现质量参差不齐。

当前可用：本仓库的 `scripts/upload.sh` 与 `scripts/session-env.sh`。

建议：提供 `board push`、`board pull`、`board ls`、`board rm` 等命令；内置令牌刷新与一次重试；显示传输进度；传输完成后校验大小与摘要；提供 shell 补全。

### 3.2 开发板内仍需手工下载，没有共享挂载

文件上传到会话目录后，开发板内仍要手工执行 `wget`，并输入完整地址。当前版本没有提供网络文件系统（NFS）、9p（一种共享文件系统协议）或其他共享挂载方式，也没有板端代理自动拉取文件。

影响：每次传输都要在串口输入长地址；多文件传输没有目录语义；无法直接读写会话目录。

建议：在开发板启动后将会话目录以只读方式挂载到固定路径，例如 `/mnt/ostool`，可选用 NFS 或 9p；若内核未编译相应客户端支持，则提供板端代理，按开发板名称拉取文件。至少应注入基地址，并提供短路径。

说明：当前内核是否支持 NFS 客户端尚未验证，采用前需要确认。

### 3.3 非终端环境静默失效

ostool 仅在标准输入与标准输出都是终端时转发串口输入。通过管道或脚本调用时，输入不会被转发，但也不会报错，进程看起来正常运行。

影响：自动化脚本以为命令已经发送，实际开发板没有收到；排查时很难定位。

当前可用：用 `script(1)` 提供伪终端（pty）并保留日志。

建议：检测到非终端环境时直接报错，或自动分配伪终端；提供不依赖终端的命令模式；在帮助信息中说明这一限制。

### 3.4 没有内置日志与结构化输出

当前版本没有提供保存会话日志的选项，本仓库只能用 `script(1)` 包装。日志行尾带有回车换行（CRLF），提取字段时需要额外处理。`board ls` 与 `board connect` 的输出面向人阅读，没有 JSON 等机器可读格式。

影响：日志与字段提取依赖外部工具；受回车换行影响，脚本容易取到错误值；难以接入持续集成（CI）。

建议：提供 `--log <file>`，并统一为换行符；为 `board ls`、`board connect` 提供 `--json`；固定输出字段，例如会话编号、开发板、镜像、上传地址与共享地址。

### 3.5 上传接口的限制没有封装

上传接口有几项固定限制：单个文件不得超过 64 MiB；没有分块或断点续传；没有进度显示；返回的 `http_url` 可能为空；令牌过期时返回 401，需要先执行 `board ls` 刷新；没有摘要校验。

影响：较大文件直接返回 HTTP 500；下载地址需要用户自行拼接；令牌失效后脚本继续使用旧值；传输结果无法验证。

建议：实现分块与断点续传；显示进度；返回 `tftp_url` 与 `http_url` 两个可用地址；令牌过期时自动刷新并重试一次；传输完成后提供摘要；对 64 MiB 限制给出明确提示，而不是返回 500。

## 4. 退出与终端状态

### 4.1 退出按键失效，终端状态被破坏

在 U-Boot 提示符下，按 `Ctrl+A`、松开后按 `x` 可以退出。进入 Alpine 后，同样的操作不会退出连接：`Ctrl+A` 被 shell 的行编辑器当作“移到行首”，随后输入的 `x` 被插入命令行。通常只能在另一个终端执行 `pkill`，终止 ostool 进程。

`pkill` 之后，原终端的属性没有恢复，回显与行缓冲处于异常状态，需要执行 `reset` 才能继续使用。

影响：每次退出都要两个终端配合；终端状态损坏会影响后续命令；强制终止可能丢失尚未显示的输出。

当前可用：在另一个终端执行 `pkill -f 'ostool board connect'`，回到原终端后执行 `reset`。

建议：改用不与常见 shell 冲突的前导键，例如 `Ctrl+]`；或在任何退出路径上处理 `SIGTERM`、`SIGHUP` 与 `SIGINT`，恢复终端属性；提供 `ostool board disconnect` 命令，使退出不依赖按键序列；异常退出时打印恢复终端的提示。

说明：前导键为何被下游 shell 消费，需要上游确认；从现象看，按键没有到达 ostool 的转义处理。

## 5. 文件位置与配置兼容

### 5.1 配置写入 ~/.ostool

配置文件位于 `~/.ostool/config.toml`，没有遵循 XDG 基础目录规范（XDG Base Directory Specification）。按该规范，配置应位于 `$XDG_CONFIG_HOME/ostool/config.toml`，`XDG_CONFIG_HOME` 未设置时回退到 `~/.config/ostool/`。

影响：主目录中多出一个不透明的目录；负责备份、同步与迁移的工具通常只覆盖 `~/.config`，容易遗漏；与其他命令行工具的约定不一致。

建议：按 XDG 规范解析配置路径；同时读取旧路径，并在首次使用时提示迁移；在文档中说明查找顺序。

说明：本工作区的 Nix 包装器会把 `~/.ostool/config.toml` 替换为指向 Nix 存储的符号链接，因此该问题在当前环境中被部分掩盖。

### 5.2 凭证回退到配置目录

凭证优先保存在系统密钥环。密钥环不可用时，登录状态写入 `~/.config/ostool/hosts.json`。凭证属于运行状态，不属于配置，应位于 `$XDG_STATE_HOME/ostool/`，`XDG_STATE_HOME` 未设置时回退到 `~/.local/state/ostool/`。

影响：配置目录中混入凭证；配置目录常被同步或备份，增加泄露风险；配置与状态的职责不清。

建议：密钥环优先；回退路径改为状态目录；文件权限设为 0600；在文档中说明凭证的存放位置与迁移方式。

说明：本仓库的 `scripts/session-env.sh` 目前按 `~/.config/ostool/hosts.json` 查找；上游改为状态目录后，脚本需要同步修改。

### 5.3 版本升级破坏配置兼容性

0.31 版本删除了顶层的 `shell_prefix`、`shell_init_cmd`、`success_regex`，要求改用 `shell_check_steps`。旧配置在新版本中直接报错，提示“removed U-Boot config key”，没有迁移说明。

影响：升级后原有工作流立即失效；用户需要对照新旧格式手工改写；版本差异没有集中记录。

建议：配置文件增加版本号；读取到旧键时给出警告并自动迁移；发布迁移对照表；在同一大版本内保持向后兼容。

## 6. 错误信息与项目假设

### 6.1 错误信息不指向解决办法

常见错误缺少可操作的信息：

- 上传返回 404 时只提示会话不存在，不区分会话过期与编号输错。
- 指定 `--board-id` 被拒绝时，不说明实际分配到了哪一块开发板。
- `board run` 报 `shell check sequence ended before ... completed` 时，不说明是会话被回收还是命令没有执行。

影响：只能反复尝试；每次尝试都会消耗一个会话；定位问题依赖经验。

建议：为错误定义稳定的编号；在信息中包含请求值与实际值；给出下一步操作，例如“重新导出会话编号”或“去掉 `--board-id`”；区分可重试与不可重试的错误。

### 6.2 board run 假定项目是 Cargo 工作区

`board run` 会检查 `Cargo.toml` 与 `src/lib.rs`。非 Rust 项目即使已经提供编译好的内核，也需要创建这两个文件来满足检查。

影响：C 或汇编项目需要额外的占位文件；用户不清楚检查的目的；构建配置与项目实际结构不一致。

建议：提供不依赖 Cargo 的运行方式，例如直接指定 ELF 路径与构建命令；在缺少 Cargo 元数据时给出明确说明，而不是要求创建空文件；在文档中写明最小要求。

## 7. 改进顺序

按可执行范围分组，不按主观优先级排序：

| 范围 | 事项 |
|---|---|
| ostool 可独立完成 | 退出方式（4.1）、稳定下载地址（2.2）、XDG 路径（5.1、5.2）、会话上下文（2.1）、上传与下载命令（3.1）、日志与 JSON 输出（3.4）、错误信息（6.1）、输入节流（1.4） |
| 需要平台配合 | VPN 或跳板机接入（1.1）、开发板选择与镜像信息（1.2）、会话时限（2.4）、分离与重连（2.3） |
| 需要内核与系统验证 | NFS 或 9p 共享挂载（3.2）、U-Boot 板级配置档案（1.5） |

其中 XDG 路径、退出方式与稳定下载地址的改动范围较小，可以先做；VPN 接入需要网络与权限配合，周期最长，但能从根本上解决串口输入的问题。
