# 文档规范

适用对象：K3 工作区内的正式文档与 agent 工作记录
维护位置：`docs/agents/doc-conventions.md`

本文记录文档的目录职责、结构、行文与用语约定。后续新增或修改文档时按本文执行。

## 1. 目录职责

| 目录 | 用途 |
|---|---|
| `docs/` | 正式文档。面向读者，结构稳定，结论可复核 |
| `docs/agents/` | agent 工作记录。允许随排查过程增删，不作为正式文档 |

- 正式文档中的结论应能在工作记录、命令输出或实测记录中找到依据；没有依据的内容不写入。
- 工作记录可能包含已经过时的结论；正式文档引用之前应先复核。
- 正式文档引用工作记录时，写明具体文件与章节。
- 本文件位于 `docs/agents/`，但为了便于查阅，仍按正式文档的用语书写。

## 2. 文件命名

- 正式文档使用小写英文单词与短横线，例如 `ostool-basics.md`、`alpine-recovery.md`。
- 正式文档不加数字前缀。`docs/agents/` 中的工作记录可以沿用数字前缀。
- 一个主题一个文件，不把互不相关的操作合并到同一篇。
- 文件名应说明内容，不使用缩写。

## 3. 文首信息

正式文档在标题之后给出以下字段：

```text
适用硬件：板型与芯片，例如 BananaPi BPI-SM10（SpacemiT K3）
适用系统：镜像版本与必要前提，例如已完成修复的 Alpine 3.23.4
适用工具：工具名称与版本，例如 ostool 0.31.1
记录时间：YYYY-MM-DD
相关文档：相对路径链接
```

- 第一段说明本文的范围与不涉及的内容。
- 范围只在文首完整声明一次；正文需要时引用文首，不重复条件。
- 已有文档在下次修改时补齐上述字段，不为格式单独改写。

## 4. 章节结构

- 按操作顺序或因果顺序排列。上一章结束时的状态是下一章的起点。
- 每章只解决一个问题。章节标题使用名词短语，不使用疑问句。
- 一项事实只写一次。后文需要时写“见第 N 章”，不重复解释。
- 不写结尾总结。最后一项事实陈述完毕即结束。
- 编号使用 `## 1.` 与 `### 1.1`，不超过三级。
- 一篇文档只有一个一级标题，标题末尾不加句号。
- 表格只用于对照关系，例如地址、参数、版本与状态，不用于承载叙述。
- 长文可以在开头用一段说明章节关系，但不重复各章内容。

## 5. 行文

- 使用书面语，避免口语、网络用语与拟人。
- 优先使用双音节词。例如“查看”而非“看”，“修改”而非“改”，“输入”而非“敲”，“运行”而非“跑”。
- 不使用宣传性词汇，例如赋能、闭环、抓手、完美、极致、颠覆。
- 不使用固定的对偶结构，例如“不是 X，而是 Y”“不仅 X，更 Y”。
- 不使用空洞的开场与结尾，例如“随着……的发展”“未来可期”。
- 避免“进行 + 动词”。“对配置进行检查”改为“检查配置”。
- 避免连续段落使用同一句式，段落长度不必一致。
- 命令与说明分开：先列出命令，再用一句话说明结果或前提。
- 引用界面输出时保持原样，不转述为评价。
- 使用中文标点；中文与英文、数字之间加空格。
- 行内的命令、路径、字段名与文件名使用反引号。

常用替换：

| 不使用 | 使用 |
|---|---|
| 看 | 查看 |
| 改 | 修改 |
| 敲 | 输入 |
| 跑 | 运行 |
| 装 | 安装 |
| 硬限制 | 硬性限制 |
| 掉字 | 字符丢失 |
| 卡住 | 无法继续 |

## 6. 用语与术语

| 类别 | 处理 | 示例 |
|---|---|---|
| 命令、路径、参数、寄存器、文件名 | 原样保留 | `tftpboot`、`/dev/sda3`、`0x102200000` |
| 协议名、项目名、工具名 | 保留英文 | U-Boot、DHCP、TFTP、SSH、NFS、9p |
| 有稳定中文说法 | 使用中文 | 根文件系统、设备树、启动参数、会话、运行级别、开发板 |
| 首次出现 | 中文（英文原名） | 根文件系统（rootfs） |
| 代码块与表格 | 不解释、不括注 | — |

- 一个词在一篇文档中只用一种写法。“开发板”不写成“板子”。
- 不新造缩写。“会话编号”不写成“SID”；`SID` 只作为脚本中的环境变量出现。
- 不使用没有解释的行业词，例如“门禁”“基线”。
- 缩写第一次出现在正文时，给出全称与一句中文说明；只在代码块或表格中出现时不解释。
- 术语译法按现有文档的实际用法，不自行创造新译名。

## 7. 事实与范围

- 只写实测或可查证的内容。没有验证的写成“尚未验证”或“需要确认”，不写成结论。
- 区分现状与建议。现状使用陈述句；建议以“建议：”引出。
- 数字、版本、地址与校验值保持原样。校验值随输入变化时，说明“以本次输出为准”，不写死具体值。
- 不写口令、令牌、私钥与会话 cookie。示例使用占位符，例如 `<root 口令>`。
- 不把推测写成因果。无法确认原因时，写“从现象看”，并说明需要确认的部分。

## 8. 代码与命令

- 代码围栏必须成对，并标注语言：`bash`、`sh`、`text`、`toml`。
- 命令、路径、地址与输出保持原样，不翻译、不美化、不调整缩进。
- 占位符使用 `<...>`，并在代码块之后说明需要替换的内容。
- 长命令拆成多行或使用变量，避免在串口等不可靠链路上一次输入过长。
- 不在命令示例中写明文口令，使用环境变量或 `read -rs`。
- 需要校验的输出，给出期望值或校验方式，不只写“成功”。

## 9. 跨文档一致性

- 同一事实在不同文档中只能有一种说法。
- 修改一处结论时，检查其他文档是否引用同一事实，并同时修改。
- 跨文档引用写明文件名与章节号，例如“见 [`ostool-issues.md`](ostool-issues.md) 4.1 节”。
- 文档中出现的脚本、路径与命令必须真实存在；示例性质的内容明确标注。
- 提交前用 `grep` 检查同一术语的不同写法。

## 10. 写作流程

1. 收集素材：会话日志、命令输出、脚本与上游文档。
2. 先确定范围与章节关系，再写正文；不在中途改变结构。
3. 按实测事实写初稿，不补充未经核实的内容。
4. 成稿后用 `shuorenhua` 做一遍语言清理，只改表达，不改事实、数字、命令与路径。该 skill 已全局安装，可通过 `@shuorenhua` 调用。
5. 对照第 11 节逐项检查。
6. 提交信息使用 `docs: ` 前缀，说明新增或修改的内容。

## 11. 交付前检查

```text
[ ] 文首包含适用硬件、适用系统、适用工具、记录时间与相关文档
[ ] 第一段说明范围与不涉及的内容
[ ] 每章只解决一个问题，章节之间没有跳跃
[ ] 同一事实没有在多个章节重复解释
[ ] 代码围栏成对，并标注语言
[ ] 命令、地址、版本与校验值与实测一致
[ ] 没有口令、令牌与私钥
[ ] 术语全文统一，缩写首次出现有说明
[ ] 跨文档引用指向正确章节
[ ] 没有结尾总结与宣传语气
```
